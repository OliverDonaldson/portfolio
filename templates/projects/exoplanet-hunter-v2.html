Exoplanet Hunter V2

A calibrated deep-learning platform for vetting transit candidates in NASA TESS, Kepler and K2 photometry — running live, with a promotion gate that is allowed to say no.

The candidate catalogue: 12,472 scored targets, ranked highest-probability first, with the per-row spread across the five folds and the Kempton follow-up metrics a reviewer would actually sort on.

What It Does

A space telescope produces far more candidates than anyone can examine by hand, and most periodic brightness dips are not planets — they are eclipsing binaries, background eclipses bleeding into the aperture, instrumental systematics, or stellar variability. Separating those is called vetting, and it is the bottleneck in the field.

Given a known signal — a TOI, a KOI, or an ephemeris you supply — Exoplanet Hunter returns the probability that it is a planet, together with the diagnostic evidence behind that probability, so that follow-up telescope time goes to the candidates that deserve it.

The scope, stated plainly: this classifies signals that other pipelines already detected. It does not search for new ones. Being precise about that boundary is the difference between a useful triage tool and an overclaim.

The Pipeline

Every stage is reproducible from the catalogue queries down, and every artefact it produces is versioned:

  • Catalogue refresh
  • Validation gates
  • Phase-folded views
  • 5-fold CNN ensemble
  • Platt calibration
  • Promotion gate
  • FastAPI scoring
  • Vetting console

The model is a dual-view 1D CNN over the global and local phase-folded light-curve views plus nine scalar features, trained across five folds. MC-Dropout attaches an uncertainty estimate to every score, and Platt scaling fits the calibration once over the averaged ensemble — not per member and averaged afterwards, because the ensemble is what gets served, so the calibration has to describe it.

A Prefect flow runs the whole refresh weekly: pull the catalogues, run the Pandera validation gates, train only if the gates warrant it, put the result through the promotion gate, and publish only if it passes.

The Console

The console is the deliverable — the thing a stranger opens. It has to show not just the number but how the number was produced, because a probability a reviewer cannot interrogate is a probability they cannot act on.

Vetting TOI-4328.01: a calibrated 0.894 ± 0.246, the follow-up priority metrics, and a stage-by-stage trace of exactly how that number was produced — every figure on the page coming from the one scoring response.

It is one static file: plain HTML and JavaScript with anime.js inlined at build time, no bundler and no framework. An earlier React build existed and was deleted in September 2026 — it had not shipped in weeks, and the static console did the job with a fraction of the surface area.

Beat the Baseline Before You Cheer

The rule that governs the whole repository: a model ships only if it beats the champion's cross-validated ROC-AUC without losing calibration or shortlist recall. Nothing is promoted because it looks better.

Every margin is read against a noise floor — the seed-to-seed spread of the same metric measured in the same run. A model that beats the champion by less than the run's own reseeding noise has not beaten anything, and the gate is built to say so. Since August 2026, every single attempt to replace the dual-view champion has been rejected by that gate. Two results cleared their floors, and both of them complemented the champion rather than replacing it.

Publishing a null result is a result. The branch-model line — months of work — is closed in writing, with ca906040 still served, because the evidence never justified promoting anything over it.

A separate command, make ready, answers whether the repository is fit to show — and nothing else is allowed to answer it. It checks that the report PDF is current, that every figure it references resolves, that no documentation link is dead, that the registry names a run whose artefacts are actually on disk, and that the deployed API and console both answer. It prints LOOKS GOOD or NOT YET. No document claiming the project is finished counts for anything.

What It Can't Do

The project keeps a register of its own measured weaknesses, and the report states them before it states any result. The honest summary:

  • It is behind the published state of the art on the metric that matters. On recall at a 1% false-positive rate, ExoMiner and ExoMiner++ sit roughly 12 points ahead on Kepler and roughly 64 points ahead on TESS. A formal comparability audit found that of six candidate comparisons, five could not be stated either way on population or protocol grounds — and the one that was comparable was unfavourable. It is written up that way.
  • There is no measured classical baseline. A Random Forest baseline exists in code with a documented rationale, but no scored cross-validated result for it exists in the repository. The CNN's advantage over classical ML is assumed here, not measured — and the docs say so.
  • Ranking is partly driven by observation baseline, not physics. On TESS, how long a target was observed correlates +0.387 with its label. That bias is in the labels themselves, so no architecture can reach it; propensity weighting removed the model's amplification of it, but not the underlying cause.
  • The decision metric is an eight-to-ten row statistic. TESS recall @1% FPR is cut at roughly the tenth-highest negative score, which gives it a paired sampling standard deviation of 0.044. Any architecture effect smaller than about 0.09 on that metric is undetectable at this sample size, however many models get trained.

None of that stops the project being worth showing. What would stop it is a reader finding a claim they cannot check, a dead link, a figure that does not exist, or a number on the live site the API never served.

The wire contract between them is a single schema file, and a contract test fails CI if the console and the API ever disagree about it.

Development & AI Collaboration

I built this in VS Code with Anthropic's Claude via the Claude Code CLI, used as a pair-programming and tutoring collaborator. The approach was deliberately learning-first: as a data-science student rather than an astronomer, I used it as a sounding board and scaffolding tool, then took ownership of the pipeline — verifying every design choice, reading the peer-reviewed papers behind each component, and refining the system through independent research. The scoping, the judgement about what counts as evidence, and the decision to close the branch line rather than ship it are mine. The full methodology, references and limitations are in the report linked above.

What I Took From It

The technical work — calibration, leakage-safe validation, ensembling, orchestration, deployment — is the part that shows up in a stack list. The part that actually changed how I work is narrower: learning to build the gate that tells you your idea failed, and then believing it. Most of what I tried in this project did not beat the thing I already had. Measuring that properly, writing it down, and shipping the older model anyway was harder and more useful than any individual architecture change.
